# Path-of-craft-tree: оптимизация

Спецификация первого круга оптимизации. Цель владельца: мод меньше нагружает сервер, у клиента нет просадок кадров, обмен между клиентом и сервером идёт без задержек.

Журнал замеров и решений ведётся в [perf-log.md](perf-log.md).

## Исходные условия

- Обе половины мода собираются из одного набора модулей в `mixins/path_of_craft_tree`. Сервер — `horizon-engine`, клиент — `horizon-client`.
- Модули без зависимости от игры (`rules`, `look`, `view`, `placed`, `*_rules`) собираются отдельно через `lib.rs`. На них работают тесты и бенчмарки criterion.
- Игровые модули отдельно не собираются. Их стоимость измеряется в игре счётчиками времени, это раздел «Замер в игре».
- Замеры проводятся только на свободном ПК: без записи экрана, без других серверов и задач на видеокарте. Базовая и повторная линии снимаются на одной машине и в одном профиле сборки.

## Горячие пути и бюджеты

| # | Путь | Частота | Бюджет |

| S2 | `break_speed` на сервере и клиенте: `mining`, `fx_gather`, `fx_craft_build` | каждый тик копания | ≤ 2 мкс на вызов |

| S5 | Тик сервера `glue::on_server_tick` | каждый тик | ≤ 20 мкс без сохранения |

Бюджеты заданы до замеров и могут уточниться после базовой линии. Ни один бюджет не оправдывает изменение поведения: все 120 тестов правил и проверенные в игре эффекты должны работать как раньше.

## Замер в игре

Сборка для замеров — `dev.ps1 both -BuildProfile performance -Perf`. Профиль `dev` у движка собирается без оптимизаций (`opt-level` 0), и его цифры ничего не говорят о том, что получат игроки. `performance` — это профиль лаунчера по умолчанию: release без LTO, с инкрементальной сборкой.

В сборку добавляется модуль счётчиков: число вызовов и суммарное время в наносекундах по каждому пути из таблицы. Каждые 30 секунд они пишутся в журнал. Счётчики включаются переменной сборки `PCT_PERF`. Без неё код счётчиков отсекается при компиляции, и в сборки для игроков он не попадает.

Профиль процессов игры и сервера снимается xperf с выборкой стеков во время того же сценария.

Сценарий одинаковый для базовой и повторной линии:

- выделенный сервер на 127.0.0.1;
- один игрок с полным демонстрационным профилем;
- 60 секунд копания камня и руды;
- 30 секунд в открытом окне дерева: общий вид, приближение, наведение на узлы;
- одно включение Рудного нюха.

## Бенчмарки criterion

Файл `benches/rules.rs`. На входе — настоящее дерево `data/tree.json` и профиль с изученными ветвями. Бенчмарки после написания замораживаются.

- `effects_clone` — копия полного словаря эффектов игрока, то есть то, что сейчас делает `player_effects` на каждый вызов.
- `tree_effects` — пересчёт эффектов профиля.
- `award` — начисление опыта с перекрёстной веткой.
- `standing_new` — состояние окна дерева на кадр (`look::Standing::new`).
- `sanitize` — проверка загруженного профиля при входе.
- `tree_parse` — разбор дерева, который клиент делает при каждом входе.

## Правило приёмки

1. Медиана нового времени к старому ≤ 0,95 на целевом бенчмарке или счётчике, остальные не хуже 1,03.
2. Перед первой правкой выполняется A/A-прогон. Если шум больше 5%, `measurement_time` увеличивается.
3. Перед слиянием должны проходить проверки:
   - `cargo fmt --check` на изменённых файлах;
   - clippy с `-D warnings -A dead_code`, потому что игровых вызывающих в обвязке тестов нет;
   - `cargo test`;
   - сборка обеих половин через `dev.ps1 both`.
4. Каждая гипотеза проверяется отдельной веткой и записывается в журнал, принятая или отклонённая.

## Предварительные гипотезы

Взяты из карты горячих путей. Порядок проверки определится после базового замера.

1. `player_effects` и `client().effects` копируют весь словарь эффектов (около 285 ключей-строк) на каждый вызов, в том числе на каждый тик копания и каждый тик игрока. Предлагается хранить эффекты в `Arc` и отдавать дешёвую копию указателя. Пути: S1, S2, S4, C2.
2. `award_main` и `award_cross` копируют весь профиль вместе с растущим множеством `seen`. Предлагается начислять опыт на месте через `&mut Profile`. Путь S3.
3. Окно дерева каждый кадр копирует профиль, считает `Standing` и обходит все связи. Предлагается пересчитывать `Standing` только при новом состоянии профиля, а обходить только видимые связи. Путь C1.
4. Фон окна — 1,6–2 тыс. вызовов `native_sprite` за кадр. Предлагается сократить число вызовов. Путь C1.
5. Рудный нюх выделяет строку на каждый блок куба. Предлагается проверять руду без выделения памяти и распределить сканирование по кадрам. Путь C3.
6. Обход всех мобов и станций на каждого игрока. Предлагается один проход на тик для всех игроков. Путь S1.

Найденный при разборе баг (бонус уровня ветки не обновлялся при получении опыта) исправлен до оптимизаций, коммит `34f9c4a`.
